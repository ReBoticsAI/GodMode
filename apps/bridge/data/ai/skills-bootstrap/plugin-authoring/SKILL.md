Use when the change adds ObjectTypes, routes, web pages, AI tools, department types, external APIs, or hardware. Do not only call `create_department` for functional domains.

1. Read `docs/PLUGIN_AUTHORING.md` for manifest and register API shape.
2. **New domain / list / inventory-style plugin (preferred):** when the USER wants a new plugin with its own durable data, prefer `run_workflow` with `workflowId: "scaffold-domain-plugin"` and input `{"id":"<kebab-id>","name":"<display name>"}`. That seeded graph runs plugin-authoring → domain scaffold → implement → build → install → prove create/list on `openPluginDb`. Fall back to the manual tool chain below only if the workflow is missing, disabled, or fails with a clear engine error.
3. Prefer declaring **ObjectTypes**, operations/actions, and optional `records` seeds when Core personal-OS or adapter-façaded. Vocabulary: ObjectType / Field / Record (not DocType). Call `use_skill('object-types')` for metadata detail.
4. `scaffold_plugin` with a kebab-case id creates `godmode.plugin.json`, `src/bridge.ts`, `src/web.tsx`, and package.json under `plugins/<id>/` from **versioned trees** in `apps/bridge/data/scaffolds/`:
   - `template: "domain"` (**default**): plugin business data via `host.openPluginDb` → `plugin-data/{tenant}/{plugin}.sqlite`. Manifest stamps `dataPlane: "domain"` and `scaffoldTemplate: "domain"`. Native workspace ObjectType tables are **rejected** at build/activate. Use for any plugin-owned durable state.
   - `template: "records"`: Core personal-OS ObjectTypes / workspace Records only (`dataPlane: "core-records"` + `scaffoldTemplate: "records"`). Do not use for plugin business data. Do not set `dataPlane: "core-records"` alone to bypass the gate.
5. Bridge exports `register(api)`; web exports `registerWeb(api)`. Executable manifests declare `kernelApiVersion: 1`. Service-backed ObjectTypes use `api.objectTypes.register(definition, adapter)` and implement every declared capability. Domain ObjectTypes should façade into plugin SQLite, not create business tables on the tenant DB.
6. Seed StructureNode / domain Records in manifest `records` or `tenant:install`, then `build_plugin` → `install_plugin` (no Bridge restart for tools, ObjectTypes, `api.routes.mount`, or tenant:install). Community Cloud: no live **workspace** SQLite handle (`getTenantDb` is structure-seed only). Use `host.openPluginDb(pluginId, tenantId)` for plugin business tables (same path as Local/Official). Structure: `INSERT OR IGNORE INTO structure_nodes` via host IPC or `api.kernel.create("StructureNode", ...)` when granted.
7. Web UI: call `use_skill('shadcn-ui')` for tokens/composition. Import host shadcn from `@godmode/web-host` (`Button`, `Card`, `Empty`, `Badge`, `Alert`, `Tabs`, `Separator`, `Skeleton`, `cn`, …). Do not import `@/components/ui` on Intelligence/SaaS (no `apps/web`). Do not invent parallel UI kits or hand-rolled Card/Button/Empty trees.
8. **Working UX (required before done):** Primary Buttons need `onClick`, `Link`, or form submit (no decorative Got it / Get started). Seed Structure pages that match registered page kinds (not empty department overviews). Archive / history pages need an ObjectType field or action plus a filtered list; omit the page until wired. Prefer host `record-list` for CRUD lists. Verify: `build_plugin` → `install_plugin` → `list_structure` → create or update one Record when the ask includes content. For domain plugins, prove create+list via the plugin's own tools on plugin SQLite (not workspace Records).
9. **Persistence (choose the store):**
   - **Core personal-OS entities** (notes, tasks, calendar-style Records the product owns): ObjectTypes + Records in the **workspace** tenant DB, and only with `dataPlane: "core-records"`.
   - **Plugin domain / business data** (sessions, blueprints, calculators, playbooks-style rows, plugin caches): `host.openPluginDb(pluginId, tenantId)` → `{dataDir}/plugin-data/{tenantId}/{pluginId}.sqlite`. Default for any plugin that needs its own durable tables.
   - **Workspace DB** (`getTenantDb`): Structure, install/lifecycle, kernel ObjectType registration only. Do not create plugin business tables on the tenant SQLite (Structure seed allowlist excepted). Install rejects native ObjectType materialization unless `dataPlane: "core-records"`.
   - ObjectType adapters may **façade** into plugin SQLite; they must not write domain schema into the workspace DB.
   - Ban browser `.log` file pickers/downloads and `localStorage` for durable plugin state.
   - Dirty files after reinstall/reset: migrate schema or delete and recreate the plugin SQLite file.
10. Custom Express routes must enforce authentication, tenant membership, and installed-plugin visibility. Prefer tools + ObjectTypes + tenant hooks when HTTP is unnecessary.
11. Declare strict action schemas/policies (roles, confirmation, idempotency, concurrency, retry, timeout, cancellation). Verify `OperationRun` terminal state and tenant isolation.
12. For public Community packs: Sell → **Submit to Community catalog** or `MarketplaceCatalog.prepare_submission` / `submit_submission` (static aliases `prepare_community_catalog_submission` / `submit_community_catalog_submission`). Use git/GitHub tools only for plugin development, not catalog shipping.
13. Ship coding-root changes with `git_*` tools; use Official GitHub plugin tools for PRs when installed.
14. After `use_skill('plugin-authoring')`, prefer `run_workflow` `scaffold-domain-plugin` for new domain plugins; otherwise `scaffold_plugin` (or edit under `plugins/<id>/`) over long host-repo archaeology. Few explore tools before the first write on Tier-2 asks.
